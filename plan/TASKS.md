**Non fait dans cette session** : dépôt du `.pmtiles` sur un Object Storage réel (reste local/dev), auto-hébergement Photon (reste bootstrap public), toute décision sur l'emprise géographique de production, vérification du flux Ajouter complet avec upload réel (testé uniquement isolément : Photon en JS console, pas le composant `StepDetails` lui-même dans son formulaire — nécessiterait une session WebAuthn ou une injection Redis comme en Phase 3).

**Incident d'environnement rencontré et contourné en session** (voir aussi [plan/MEMORY.md](MEMORY.md) § Infra) : le dépôt vit dans iCloud Drive ; un reboot de la machine pendant la session a laissé `fileproviderd` saturer l'I/O (70-150% CPU en continu sur plus d'une heure), rendant `node_modules` intermittemment illisible — `npx tsx src/index.ts` plantait avec une erreur interne (fichier `tsx` lu vide/tronqué), et même des commandes triviales (`tsc --noEmit`, `eslint`, `grep -r`) prenaient plusieurs dizaines de minutes au lieu de secondes. Contourné en basculant `apps/api`/`apps/worker` sur un lancement `node dist/index.js` (build `tsc` classique) plutôt que `tsx` (qui passe par esbuild, la couche qui coinçait) — une fois lancés ainsi, tout a répondu normalement. L'utilisateur a aussi basculé le dossier en "toujours garder sur ce Mac" en cours de session.

**Bugs réels trouvés et corrigés pendant la vérification** :
- `pnpm typecheck` : décoration Fastify `search` en collision de type avec la méthode HTTP native `fastify.search()` (renommée `fastify.meilisearch`) ; deux cas `noUncheckedIndexedAccess` dans `ExplorerMap.tsx` (déstructuration de `Position` GeoJSON, assignation de classe CSS Modules à `element.className` natif). Détail dans plan/MEMORY.md.
- `next build` échouait sur `Html should not be imported outside of pages/_document` — message sans rapport apparent avec la vraie cause (`maplibre-gl` importé statiquement fait planter le rendu SSR que Next tente même pour une page `"use client"` lors de la génération statique). Corrigé en import dynamique `next/dynamic({ ssr: false })` pour `ExplorerMap` dans `apps/web/app/page.tsx`. Confirmé responsable en comparant un build avant/après `git stash` des changements Phase 4 (Phase 3 seule buildait proprement).
- Carte confinée à ~67px de hauteur au lieu de remplir tout `.mapArea` : `height: 100%` sur un enfant statique d'un conteneur dont la hauteur vient d'un `flex: 1` est ambigu selon les moteurs de rendu. Corrigé en `position: absolute; inset: 0` contre l'ancêtre `position: relative`, voir `ExplorerMap.module.css`.
